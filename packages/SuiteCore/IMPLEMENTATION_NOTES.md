# Suite Core implementation boundary

The public `RecipeParameters`, `EditHistory`, `AssetRecord`, `ProjectCheckpoint` and `ProjectStore` APIs retain the shared contract. Implemented source and authored tests are not native build/device-verification evidence.

## Editing and persistence

`RecipeParameters` stores the four wired controls, all 18 RAW control contract names, explicit processing order and data-only extensible parameters for RAW, Portrait, Body, Look and future settings. Persisting those settings does not implement rendering them. Providers must reject unsupported settings instead of silently producing an incomplete Final.

History stores parameters, optional editor reference and time. Undo/Redo round-trip with the entire history. Editing after Undo removes the abandoned redo branch; no-op edits preserve it. Original asset identity is immutable during checkpoint updates.

`ProjectStore(directory:)` owns a metadata-only directory. First save is revision `0` with `expectedRevision: nil`; an update must match the persisted revision and advance exactly one. The actor and process-wide lock serialize multiple store instances within this process. JSON writes use Foundation atomic replacement; iOS writes also request complete file protection. Host integration must place metadata in protected app-private storage and handle locked-device write failures without claiming success.

Schema mismatch, unknown top-level fields, corrupt JSON/history, invalid paths/checksums, invalid numeric parameters and stale revision errors are explicit. Existing corrupt files are preserved and cannot be overwritten by create-only save. `list()` fails on corrupt checkpoints instead of hiding them. Metadata files have a configurable byte cap (default 16 MiB); hitting it fails visibly without pruning history. Original bytes are never written or removed by the store.

This is not a multi-process transaction engine, encrypted cross-platform storage, guaranteed power-loss/fsync durability, cloud CAS, cloud recovery or an automatic migration implementation. Those adapters and fault-injection proofs remain required. A project checkpoint covers one asset under the initial shared contract; complete studio/project aggregation is not implemented.

## Photo lifecycle boundaries

- Normal library/selection/preview/edit/analysis request Thumbnail/Proxy/Preview plus Recipe. Final JPEG/TIFF, high precision and redevelopment require Original. The normal hydration set excludes Original.
- Cloud safety binds exact asset, object/version, representation, checksum, verification time/expiry and all upload/server/object/metadata/permission/commit checks. Missing, failed or stale evidence blocks. This is evidence evaluation, not server verification; clients cannot attest their own cloud safety.
- `ExportReadiness` cannot return a ready Proxy. It accepts only an explicitly verified local Original reference with matching asset/checksum; the platform must actually verify file bytes/existence/access immediately before use. Offline/missing/failed downloads yield `waitingForOriginal`.
- `ExportPlan` freezes asset, original checksum, Recipe revision/parameters, format and canonical generated asset IDs. Full quality/dimension/PPI/profile/naming controls and the complete rendering pipeline are outstanding.
- Cache eviction is a pure decision, not deletion. Recipe and in-use/pinned/unsaved entries are protected. Original requires explicit eviction policy, non-Local-Only mode, reacquisition availability and fresh trusted Cloud Safe evidence. Canonical generated assets require a durable copy and cannot rely on "regenerate" because Preview must preserve Final intent. LRU/quota execution, automatic cleanup and physical deletion are not implemented.
- RAW, Storage, Camera, Generative and Payment providers are protocols only. No real provider is registered, no unsupported camera is declared Supported without an evidence reference, and no actual cloud/generation/billing success is fabricated. The existing Picasso/da Vinci gateway adapter remains pending reuse work.

Tests are authored for history branching/round-trip, corruption/schema/invalid input rejection, stale CAS, concurrent store instances, immutable Original, Cloud Safe fail-closed, access intent, cache isolation and Original-only Final readiness. Native Swift build/test execution is assigned to the main agent; this Windows contribution does not mark tests passed. On a configured Swift 6 host run `swift test --package-path packages/SuiteCore`. Actual termination, full RAW compatibility, 100/500/1000-photo batches, cross-device sync, production permissions and iPhone/iPad tests remain unverified.

## Canonical Recipe and later explicit overrides

`RecipeDocument` is the strict shared `{schemaVersion: 1, parameters: ...}` envelope. Its public initializer throws. `RecipeValue` now uses plain JSON number/string/bool/array/object values with null prohibited; this is an explicitly approved integration change in the unpublished skeleton, not a silent migration of commercial user data. `rotationDegrees` must be a JavaScript-safe integer. The shared fixture at `contracts/recipe-v1.example.json` is read by the package's golden round-trip test; the repository-level fixture must be present when testing.

`SessionLook`, `TetherSessionState` and `applicationPlan` preserve five mode names, explicit optional Personal Color direction, named person intents and independently adjustable strength levels. LOW/MEDIUM/HIGH have no invented numeric mapping. Look revisions and photo bindings are immutable snapshots; a new revision affects later captures. Existing photos require a separate explicit reapply request, and old bindings remain. Auto Apply OFF, photo exclusions, session/person exclusions and per-photo person exclusions are represented. Personal Color supports color direction keys only and cannot alter face/body or retouch strength.

Application planning requires new-photo-bound analysis, verified person association and region references; it does not copy reference-photo coordinates or apply one person's settings to everyone. Body plans require background protection. An absent adapter is `notSupported`; missing analysis is `requiresAnalysis`; full test evidence can produce only `readyForAdapter`, never a rendered image or committed edit. Tether ingest detection, on-device ML, adaptive remapping, actual per-photo adjustment calculation, masks, mode UI, queue persistence and rendering are still unimplemented integrations. Metadata serialization is not successful retouch.

Cloud Safe additionally requires `sizeMatched` and `ownerWorkspaceConfirmed`. Constructor defaults and old serialized evidence missing either become `unknown` and block readiness/eviction. `ProxyQualityPolicy` exposes thumbnail/preview/highPreview selection from caller configuration, viewport/zoom/device/network state and available local derivatives. Library downloads never request highPreview; explicit pixel inspection does not relabel a low preview as sufficient. `SyncPriorityPolicy` preserves P0 Recipe/Metadata, P1 Proxy, P2 Original, P3 optional Generated/Export, with only explicitly selected immediate-Final Originals promoted. `NetworkTransferPolicy` requires cellular opt-in and respects pause/unknown/offline; priority does not override it. These are pure decision boundaries, not background transfer, physical deletion, signed URL or provider implementations.
