# SUITE 正本 — 実装・リリース方針とSolへの引継ぎ

更新日：2026年10月3日。版：0.2。

**このファイルを、本作業で確定した方針・成果・作業状態の正本とする。** メインだけが更新・最終統合を行い、サイドエージェントのレビューや作業メモは補助資料として扱う。Solはこの正本と、引継ぎ後に取得する既存コード・確定済み仕様の原本を確認して作業を継続する。新たなユーザー指示を受けた場合も、この正本を更新して変更内容を記録し、並立する正本を作らない。

正本への固定は、この文書に書かれた「実施済み」「未実施」「未確認」を固定するものであり、未検証のアプリを完成扱いにするものではない。既存の仕様原本をこの文書で置き換えない。

## 方針名

**Mobile Release First**

SUITEでは、Web版より先にiPhone・iPad版を完成させ、リリースする。

**最初に公開する完成品をiPhone・iPad版とすること**を、実装・設計・QA・リリース判定の最優先方針とする。Web対応は、iPhone・iPad版の完成条件およびリリース条件に含めない。

## 既存仕様の完全継承

これまでの打ち合わせ、実装指示、確定済み仕様、合意済み要件をすべて継承する。

今回の「モバイル先行リリース」への変更は、**リリース順序と実装優先順位の変更のみ**であり、これまでに確定した仕様の撤回・削除・簡略化を意味しない。

モバイル先行を理由として、以下を勝手に削除・変更・置換しない。

- 既存機能
- 合意済み要件
- UI／UX
- 画面構成
- 操作導線
- 編集機能
- データ設計
- 保存仕様
- セキュリティ要件
- 安全設計
- 運用要件
- QA要件
- リリース要件
- その他、これまでの打ち合わせで確定した内容

既存仕様と今回の指示に矛盾がない部分は、すべてそのまま維持する。この文書に再掲されていない確定済み仕様も継承対象とする。

**今回後ろに回すのはWeb版の完成・公開のみであり、既存仕様そのものを落としてはならない。**

既存仕様にWeb版の完成をモバイル版の完成・公開と結び付ける条件がある場合は、そのリリース上の依存関係のみを今回の指示に合わせて変更する。仕様の内容を維持したまま優先順位を変更し、それ以外に矛盾が見つかった場合は、該当する仕様・影響を明示してユーザーに確認する。

## 適用原則

- 既存実装を破棄して作り直さず、現在のコードを基点として優先順位を変更する。
- 勝手な再設計や全面リファクタは禁止し、今ある実装を起点に必要な修正を行う。
- 既存のWeb向け共通処理は、モバイル版に適用可能であれば再利用する。
- Web UIの追加開発より、iPhone・iPad版の完成を優先する。
- Web対応がモバイル版の完成を遅らせる場合、Web版の完成・公開に向けた作業を後続フェーズへ移す。その場合も、Web向けを含む既存の共通仕様、データ構造、バックエンド仕様、将来拡張前提は保持する。
- 共通ロジックはUI層から分離し、将来のWeb版追加を妨げない構成にする。
- 今後の設計判断、実装判断、QA、リリース可否判定は、本方針と継承した確定済み仕様を基準とする。モバイル先行を理由に、機能・品質・検証範囲を縮小しない。

## 最優先で処理する作業

**難しい設計を最優先とする。** 既存コードと確定済み仕様から設計上の難所を特定し、後続実装を妨げる問題から調整する。判断理由、制約、関連仕様、変更範囲、確認方法を記録し、勝手な再設計や全面リファクタは行わない。

欠落監査を並行して進め、独立して実施できる重い実装とバグ潰しをサイドエージェントに分担する。一つの難所が未解決でも、その判断に依存しない調整・実装・テスト修正は継続する。難所の解決が前提になる変更は、結論を推測して着手しない。

この作業配分は、上記12項目の実装優先順位と依存関係の中で適用する。難しい設計の先行調査を、Web完成の前倒しや既存仕様の省略の理由にしない。

## iPhone版の設計要件

iPhone版は、片手操作とタッチ操作を前提としたモバイル専用UIとして設計する。確定済みのUI／UX、画面構成、操作導線は継承し、以下を理由に独断で再設計・省略しない。

- 主要編集操作が画面下部または親指の届きやすい範囲で完結する構成を優先する。
- 頻繁に使う操作への到達ステップを最小限にする。
- タッチ対象の大きさと間隔を確保し、誤操作を防ぐ。
- 写真プレビューを不必要に隠さず、編集結果を確認しながら操作できる構成にする。
- PC／Web向けUIを縮小して流用しない。

操作ステップ・タッチ対象・プレビューに関する補足は、前回の方針文書に記載された検討観点である。過去の確定済み仕様との照合前に、ユーザーが合意した新規要件や追加のリリース条件とみなさない。

## iPad版の設計要件

iPad版はiPhone版の単純拡大を禁止し、画面サイズと入力手段を活かしたiPad専用レイアウトを実装する。確定済みのUI／UX、画面構成、操作導線を継承する。

- 大きな写真プレビューを確保する。
- 編集パネルを必要に応じて常時表示できるようにする。
- ツール領域と写真領域を同時に表示する。
- 横向き・縦向きの双方に最適化する。
- Apple Pencil、タッチ、トラックパッド等のポインティング操作を阻害しない。
- セーフエリア、マルチタスク時のサイズ変化、画面分割を考慮する。

セーフエリア・マルチタスク・画面分割に関する補足は、前回の方針文書に記載された検討観点である。過去の確定済み仕様との照合前に、ユーザーが合意した新規要件や追加のリリース条件とみなさない。

## 共通化する領域

後からWeb版を追加できるよう、以下の共通ロジックはUI層から分離する。

- APIクライアントおよび通信契約
- 認証・認可
- データモデル
- 写真の保存・取得
- 編集状態の永続化
- 編集履歴と復元
- プリセット
- 書き出し処理
- エラー分類と再試行方針
- バックエンドとの同期処理

共通化は、既存の共通仕様、データ構造、バックエンド仕様、将来拡張前提を保持し、後からWeb版を追加できる構成にするために行う。Web UIの完成はモバイル版リリースの前提にしない。モバイル先行を理由に、確定済みのAPI契約、認証・認可、データ設計、保存仕様、安全設計、将来拡張前提を簡略化・置換しない。

## Web版の扱い

Web版はApp Store公開後の後続フェーズとする。

- モバイル版リリース前にWeb UIの完成を待たない。
- Web固有のレイアウト、入力方式、ブラウザ互換性対応は、モバイル版の完成条件に含めない。
- 共通バックエンドや共通ロジックは既存の確定済み仕様を満たすように実装し、UI層から分離する。
- Web専用作業がクリティカルパスに入った場合は、原則として後回しにする。
- Web向けの確定済み機能、UI／UX、QA要件、公開時のリリース要件も保持し、後続フェーズで実装・検証する。延期を仕様の削除や完了扱いに置き換えない。

## 初回リリースの完成判定

SUITE初回リリースの完成判定対象はiPhone・iPad版とする。以下をすべて満たし、モバイル版に適用される既存の確定済み仕様・QA要件・リリース要件を満たしていれば、Web版が未完成でもモバイル版をリリース可能とする。

以下の一覧は、既存の完成条件を置き換える限定的な機能一覧ではない。確定済みの編集機能、保存仕様、セキュリティ要件、安全設計、運用要件、QA要件、リリース要件は引き続き有効とし、Web版の完成・公開を待つ条件だけをモバイル版の判定から外す。

- [ ] 写真の読み込み
- [ ] 基本編集
- [ ] 編集内容の保持
- [ ] Undo／Redoまたは編集履歴
- [ ] 保存・書き出し
- [ ] 異常終了時のデータ保護
- [ ] iPhone実機確認
- [ ] iPad実機確認
- [ ] タッチ操作に重大な阻害がない
- [ ] 主要導線に操作不能箇所がない
- [ ] 本番用バックエンドとの正常接続

「基本編集」の記載を、確定済みの編集機能を基本機能だけに縮小する根拠にしない。「Undo／Redoまたは編集履歴」の記載を、既に確定しているUndo／Redoや編集履歴・復元の要件を減らす根拠にしない。本更新では実装・検証の証拠を確認できていないため、チェックを未記入とする。既存の検証結果を破棄・リセットするものではなく、確認できた証拠に基づいて完了を記録する。

## QAの優先順位

以下は検証の実施順序の目安であり、確定済みのQA項目・合格基準を削除・緩和しない。Web固有の検証はWeb版の後続フェーズで実施し、モバイル版および共通基盤に必要な検証はモバイル版リリース前に実施する。

1. データ消失、保存失敗、復元不能の防止
2. 写真の読み込み、基本編集、履歴、書き出しの一連の導線
3. 認証と本番用バックエンド接続
4. iPhoneの片手・タッチ操作
5. iPadの専用レイアウト、回転、Apple Pencil等の入力
6. 異常終了、通信断、容量不足等からの復旧
7. アクセシビリティと表示崩れ
8. Web UIおよびブラウザ固有の検証

## 実装判断ルール

「実装優先順位」の12項目を基準とし、同じ段階でタスク間の競合が生じた場合は、次の順で判断する。いずれも確定済み仕様を維持することを前提とし、この判断順を根拠に共通バックエンド・認証・保存基盤を後回しにしない。

1. モバイル版のデータ安全性を高める作業
2. 初回リリースの完成条件を満たす作業
3. iPhone・iPadの実機操作を改善する作業
4. App Store公開に必要な作業
5. 確定済みの共通仕様・将来拡張前提を満たしたうえで行う追加の共通化
6. Web UI固有の機能追加または改善

Web対応を同時に行う場合でも、モバイル版のクリティカルパス、品質、リリース日程に影響を与えないことを条件とする。

## 優先順位変更時の確認事項

既存タスクの順序変更や新しいタスクの追加時は、以下を確認する。本方針は確定済み仕様のスコープ変更を承認するものではない。

- iPhone・iPad版の初回リリースに必須か。
- 上記の完成判定項目、または継承した確定済み要件のどれに寄与するか。
- モバイル版のリリースを遅らせる可能性があるか。
- Web固有の要件ではないか。
- UI層と共通ロジックを適切に分離できているか。
- iPhone版とiPad版それぞれの操作性を検証できるか。
- 既存機能、合意済み要件、UI／UX、画面構成、操作導線を保持しているか。
- 編集機能、データ設計、保存仕様、セキュリティ要件、安全設計、運用要件、QA要件、リリース要件を保持しているか。
- Web向けを含む共通仕様、データ構造、バックエンド仕様、将来拡張前提を保持しているか。

App Store公開後へ移す対象は、Web版の完成・公開に向けた作業とする。移動先でも確定済み要件と検証条件を保持する。「将来向け」「今回の一覧にない」という理由で、確定済みのモバイル要件や共通仕様を独断で延期・削除・簡略化しない。

## 並列作業の分担と統合

**独立した作業は最大限並列化。ただし同じファイルや責務は被せない。統合時に既存仕様の欠落がないか確認してから完了にする。**

サイドエージェントの役割を以下に分ける。

| 担当 | 固定する責務 |
| --- | --- |
| iPhone UI | iPhone専用画面と片手・タッチ操作。既存の画面構成・操作導線との整合性。 |
| iPad UI | iPad専用レイアウト、大きなプレビュー、編集パネル、縦横表示、ポインティング操作。 |
| 編集・保存基盤 | UI層から分離する編集状態・履歴・復元・写真保存・プリセット・書き出しとデータ保護。 |
| 既存仕様の欠落チェック | 確定済み仕様と統合結果の突き合わせ、要件の欠落・変更・簡略化と検証状況の監査。 |
| メイン | 役割・担当ファイル・共有処理の境界を確定し、各担当の成果物を最終統合して実行結果と監査結果を確認する。 |

各担当の書込み可能ファイルを着手前に固定し、同じファイルの変更担当は1名だけとする。担当範囲外の変更が必要な場合はメインへ報告し、メインが担当割当を更新してから着手する。共有ファイル・共通インターフェースの変更は、メインが担当者と影響範囲を決めて調整する。サイドエージェントは他担当の成果物を上書きせず、最終統合はメインだけが行う。

同時稼働枠の範囲内で独立タスクを最大限並列化し、枠が空いたら未完了の独立タスクへ再配置する。Astra Ultraを使用する間も、一つの担当が詰まったことだけを理由に全体を止めない。詰まりの理由・依存関係・再開条件を記録し、影響を受けない作業を並列で継続する。必要な仕様や権限を推測して、詰まった処理をダミーで置き換えない。

## 実行結果と完了条件

以下の5項目を必須とする。

1. **勝手な再設計や全面リファクタは禁止。** 今ある実装を起点に必要な修正を行い、既存仕様を保持する。
2. **担当ファイルと責務を固定。** サイドエージェント間の重複を避け、最終統合はメインだけが行う。
3. **実行結果を必須とする。** 対象のビルド、テスト、主要導線の確認を実際に実行し、必要な確認を通してから実装完了とする。
4. **未完成のダミー実装を完了扱いにしない。** 仮画面、固定応答、未接続処理、保存しない保存ボタン等は、動作しているように見えても未完成として記録する。
5. **既存仕様との突き合わせ監査を最後に必ず行う。** 実装済み・未実装・壊れた箇所を洗い出し、確定済み仕様の欠落がないことをメインが確認してから実装完了とする。

各担当は、変更したファイル、対応する要件、実行したビルド・テストのコマンドと結果、主要導線の確認条件・操作・結果、未解決事項を報告する。実機確認は機種・OS・対象ビルド・確認結果も残す。メインは統合後のビルド・テスト・主要導線を確認し、個別の成功結果だけで統合後の正常動作を判断しない。

主要導線には写真の読み込み、編集、編集内容の保持、Undo／Redoまたは編集履歴、保存・書き出しを含め、既存仕様で確定している他の導線も継承する。異常終了時のデータ保護、iPhone・iPad実機、本番用バックエンドとの接続もリリース判定に従って確認する。

監査は既存仕様の出典と実装箇所・実行結果を対応付け、要件ごとに次の状態を記録する。

| 状態 | 判定根拠 |
| --- | --- |
| 実装済み | 対象の既存仕様を満たす実装と、必要なビルド・テスト・導線確認の成功結果がある。 |
| 未実装 | 対象コードを調査して機能が未実装、部分実装、または未完成のダミーであることを確認した。 |
| 壊れた箇所 | 実行時の失敗や再現可能な不具合など、仕様を満たさない証拠がある。 |
| 未確認 | 仕様・コード・実行環境・実機等が不足して判定できない。実装済み、未実装、正常動作のいずれにも推測で振り分けない。 |

未実行は成功と記録しない。必要なビルド・テスト・導線確認が未実施または失敗している場合、既存仕様の欠落が残る場合、既存仕様との照合が未確認の場合は、実装完了またはリリース可能とは扱わない。確認できた成果、残作業、阻害要因、再開条件を分けて報告し、独立して進められる作業は継続する。Web版の完成・公開のみ、上記のモバイル先行方針に従って後続フェーズへ移せる。

**これまでの打ち合わせで確定した仕様は一切落とさない。**

## Sol引継ぎ — やったこと

- 既存の方針文書を基点に、変更をリリース順序と実装優先順位に限定し、既存仕様の完全継承を明文化した。
- 実装優先順位12項目を指定順で保持し、リリース確認11項目をユーザー指定の原文に揃えた。
- 11項目だけで既存の編集・安全・運用・QA・リリース要件を置き換えないことを明記した。
- Web完成・公開の後続化が、共通仕様・データ構造・バックエンド・将来拡張前提の削除につながらないよう修正した。
- 過去AIが補足した検討観点を、合意済み仕様や新しいリリース要件と混同しないよう注記した。
- iPhone UI、iPad UI、編集・保存基盤、既存仕様の欠落チェックを分担し、担当ファイルを分離してレビューした。最終統合はメインが担当する。
- 難しい設計の最優先処理、独立タスクの並列継続、5つの実行・完了条件を本正本へ追記した。
- ローカル作業フォルダと登録プロジェクト一覧を確認し、実装再開に必要なリポジトリと確定仕様の保存先をユーザーに確認中である。

## Sol引継ぎ — 残タスク

1. SUITEの既存リポジトリと確定済み仕様全文の保存先を特定する。これは実コードの調整・ビルド・テスト修正と完全な欠落監査を進めるための不足入力である。
2. 既存コード、ローカル変更、仕様の出典、実行環境を確認する。要件と実装箇所を対応付け、難しい設計の未解決点を最優先で特定する。
3. 難所の調整案を既存仕様の範囲で具体化し、根拠・影響・検証方法を記録する。各役割の実ファイルと責務を固定し、独立した重い実装とバグ修正を並列に進める。
4. 現在の実装の調整、必要なテスト修正、ビルド・テスト・主要導線確認を行う。仕様を満たさない実装を通すためにテストの期待値を緩めたり、失敗するテストを削除・無効化したりしない。
5. メインだけが成果物を統合し、統合後のビルド・テスト・主要導線を実行する。iPhone・iPadの実機、本番用バックエンド接続、データ保護を含む既存のQA要件を検証する。
6. 既存仕様の原本と統合後の結果を最終照合し、実装済み・未実装・壊れた箇所・未確認の一覧を根拠付きで更新する。欠落・未解決不具合・未検証項目が残る場合は、それを解消するか阻害要因と再開条件を明示し、実装完了とはしない。
7. モバイル版の既存リリース要件と本正本の完成条件を満たしてからリリース準備・App Store公開へ進む。Web版の完成・公開はその後に進める。

不足入力を待つ間も、入手済みの情報で独立して実施できる文書整合・欠落監査・作業分担の整理は継続する。対象コードがない状態で、代わりのアプリや仮の基盤を新規作成しない。

## Sol引継ぎ — 変更禁止事項

- 既存機能、合意済み要件、UI／UX、画面構成、操作導線、編集機能、データ設計、保存仕様、セキュリティ、安全設計、運用、QA、リリース要件の独断による削除・変更・置換・簡略化。
- 勝手な再設計、全面リファクタ、既存実装の破棄・作り直し、ユーザーの作業変更の上書き。
- Web向けを含む共通仕様、データ構造、バックエンド仕様、将来拡張前提の削減。
- PC／Web UIの縮小によるiPhone UIの代用、iPhone UIの単純拡大によるiPad UIの代用。
- Web完成・公開をモバイル版のリリース条件へ戻すこと。
- 担当外ファイルの編集、同じファイルの重複担当、サイドエージェントによる最終統合。
- 未完成のダミー、未実行のテスト、未確認の動作を成功・実装済み・完了と報告すること。
- 既存仕様との最終突き合わせを省略し、文書レビューだけで実装完了とすること。

## Solの引継ぎ手順

Solは最初に本正本の「今の状態」「やったこと」「残タスク」「変更禁止事項」を読み、実コードと仕様原本の所在を確認する。確認済み成果は引き継ぎ、未実施・未確認の項目から再開する。優先順は難しい設計の調整、欠落監査、独立した重い実装とバグ修正とし、12項目の工程順序・依存関係を維持する。

進捗、変更ファイル、実行結果、残る不具合、未確認事項をこの正本に反映する。モデル変更や別チャットへの移管は今回実行していない。この文書はSolが作業を継続するための引継ぎ成果物である。
