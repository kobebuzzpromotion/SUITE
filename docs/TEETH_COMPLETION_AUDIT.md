# EV3-0235 Teeth — completion audit

Status: **NOT_IMPLEMENTED in SUITE as a product Teeth feature** (2026-10-04). A later, limited manual-teeth **pure pixel component and optional typed Recipe validator** exist, but have no authenticated mask-authoring host, UI, save/reload, Worker Preview/Final or real-photo proof. No AI model, billing route or candidate completion count is added.

## Official operation boundary

The official [Desktop Teeth guide](https://support.evoto.ai/teeth/), [iPad Teeth guide](https://support.evoto.ai/teeth-ipad/) and [Mobile Teeth guide](https://support.evoto.ai/portrait-retouching-teeth/) describe the same named controls. Their presence does not prove identical pixels or cross-device Recipe interchange. The official [three whitening methods guide](https://support.evoto.ai/how-to-whiten-teeth-in-evoto-in-3-quick-ways/) additionally distinguishes the Teeth sliders from Smile Generation and an automatically detected Teeth Mask under Color Adjustment.

| Frozen subitem | Documented behavior | Current SUITE / unmet boundary |
| --- | --- | --- |
| EV3-0235 Teeth Flaws Removal | Automatic AI correction of visible braces, stains or gaps, with natural texture claimed by the guide | No dental flaw detection, inpainting, repair result or per-person teeth operation. |
| EV3-0236 Fix Teeth Edge | Separate toggle repairs jagged/chipped natural-tooth edges | No tooth edge geometry, local repair processor or toggle. |
| EV3-0237 Teeth Whitening | Parent operation enabling two controls | A SUITE-only manual-mask pure pixel component now exists, but no verified mask source or product route. Global color and Face Brightness are not substitutes. |
| EV3-0238 Brightness | Brightens tooth area | Pure manual-mask brightness exists; no Editor/Save/Final route or confirmed tooth-only mask. Generic face-oval EV raises the whole face. |
| EV3-0239 Desaturation | Reduces yellowing by lowering tooth saturation | Pure manual-mask desaturation exists; no Editor/Save/Final route or confirmed tooth-only mask. Generic saturation/HSL operates beyond teeth. |
| EV3-0240 Teeth Alignment | Five levels of dental-structure correction | No alignment model, geometry/deformation algorithm or five-level control. |
| EV3-0241 adult condition | Alignment described as optimized for adult teeth | No verified age/dentition boundary or safe rejection; must not infer age from face pixels. |
| EV3-0242 Pretty Teeth | Generates a replacement set of naturally shaped teeth | No generation model or immutable generated result. This is not whitening or a minor edge correction. |

The official guides say flaw and edge repair act on natural teeth, **not** teeth generated by Smile Generation. They do not publish exact algorithms, pixel reference outputs, slider numerical bounds, credit/billing semantics or a cross-platform file contract. The separate masking tutorial says Evoto automatically detects teeth for the Color Adjustment mask; SUITE does not. Do not merge the three whitening methods into one claimed implementation or invent a tooth mask from a face oval.

## Current SUITE code and safety boundary

The [face detector](../apps/web/src/processing/faces.mjs) derives a **face-oval polygon** from the bundled Face Landmarker and deliberately exposes no dental landmarks or tooth segmentation as a product result. The [portrait Recipe validator](../apps/backend/src/portrait-recipe.ts) accepts only `adjustmentType:'face_brightness'`. At the original audit, generic [photo-policy](../apps/backend/src/photo-policy.ts) **did structurally accept** an invented `extendedParameters.teeth` object while the [renderer](../apps/web/src/processing/pure.mjs) rejected it. This was an integration gap, not support. The subsequent contract change rejects that invented alias with `INVALID_TEETH_MANUAL_ALIAS` and accepts only a typed optional `extendedParameters.teethManual` document. The typed document stores Asset UUID, Original SHA, full dimensions, person UUID, bounded normalized ADD/ERASE strokes and brightness/desaturation; it stores no bitmap, saved revision or self-declared permission evidence. [Manual-teeth-whitening.mjs](../apps/web/src/processing/manual-teeth-whitening.mjs) is a separate deterministic mask-gated sRGB8 pure processor. Its `ownerConfirmed` and mask provenance fields are caller assertions, **not** authentication or proof the mask actually selects teeth. It remains disconnected from production Editor, Session, Worker Preview/Final and real Asset/person authority. The existing face brightness value is applied across the face oval, not the mouth or individual teeth. The [Editor](../apps/web/src/editor-ui.mjs) only offers selected-person Face Brightness. Its [Session](../apps/web/src/session.mjs) can save/reload/Undo/Redo and export **that** operation, but these plumbing capabilities do not make any of the eight Teeth subitems functional. Real-person processing is also held behind the existing [privacy approval gate](../apps/web/src/person-privacy.mjs), not bypassed by a new UI label.

The [dedicated audit regression](../apps/web/tests/teeth-completion-audit.test.mjs) preserves the old asymmetry as history, then tests the present fail-closed contract: invented `teeth` is rejected at Recipe validation; typed `teethManual` passes structural validation but is still rejected by the Web renderer. A `teeth_whitening` portrait target is rejected by the typed portrait validator. These are absence and safety tests, not dental pixel-quality tests. The separate new pure-component and Backend contract tests cover only synthetic pixels and JSON boundaries.

## Smallest potentially safe non-AI path (parts implemented, product route unapproved)

A **manual, explicitly painted teeth-only brightness/desaturation** path could be a limited SUITE-specific subfeature, not automatic Evoto Teeth Whitening. The typed Asset UUID/Original SHA/full-dimension/person-bound stroke **structure** and pure sRGB8 mask-gated processor are now implemented and synthetically tested. The processor leaves outside-mask pixels, alpha, hidden RGB and Original inputs unchanged. The missing next gates are a fresh authenticated host that proves the Asset/person/revision and actual owner-authored mask provenance, user review that keeps lips, skin, gums and braces outside the mask, and Preview, Undo/Redo, CAS save/reload and Final with mask projection tests for Proxy/RAW dimensions and before/after verification. It must fail closed for missing/ambiguous mask, other Asset/SHA, expired permission and unsupported dimensions. Owner approval and representative real-photo/RAW quality tests are required before claiming even this limited operation.

That manual path would **not** implement automatic teeth detection, AI flaw repair, edge rebuilding, five-level adult alignment, or Pretty Teeth generation. Those need separate model/privacy, identity, dental-quality and result-lifecycle gates. The 44-candidate completion count remains unchanged.
