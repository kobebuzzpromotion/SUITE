# EV3-0001 Makeup / Highlight — completion audit

Status: the source's **automatic Makeup / Highlight remains NOT_IMPLEMENTED in SUITE** (2026-10-04). The original audit added no processor, UI or Recipe field. Subsequent work added a SUITE-only manual pure processor and typed Recipe structure, but no product UI, save authority, Worker Preview/Final or automatic face-zone selection. The candidate completion count is unchanged.

## Frozen source operation

The [Desktop Makeup guide](https://support.evoto.ai/makeup/), [iPad Makeup guide](https://support.evoto.ai/makeup-ipad/) and [Mobile Makeup guide](https://support.evoto.ai/portrait-retouching-makeup/) describe a Highlight/Highlights control that brightens **key facial areas** for a luminous, dimensional appearance and has an intensity slider. Each guide says the Makeup module automatically identifies the face and relevant areas. The [frozen master row](EVOTO_AUDIT/EVOTO_FEATURE_MASTER.md) records **EV3-0001, Portrait → Makeup / Highlight → Highlight → Intensity**. This is one candidate control, not the entire Makeup Suite. Contour, eyebrow, eye and lip makeup are separate operations in the guides and neighboring candidate rows; they must not be silently counted as subcontrols of EV3-0001.

The sources do **not** publish a numerical slider range, exact face-region mask, color/lighting equation, reference pixel output, Recipe representation, or proof of cross-platform pixel equivalence. A secondary web alias may call the slider “Amount”, but the frozen audit labels that relationship a candidate, not processing equivalence. We therefore cannot assert that a similarly named SUITE control reproduces this operation.

## Current SUITE overlap versus unique gap

| Existing SUITE operation | Actual overlap | Why it is not Makeup / Highlight |
| --- | --- | --- |
| Global `highlights` in [color-adjustments.mjs](../apps/web/src/processing/color-adjustments.mjs) | Brightens a tonal range in the rendered sRGB8 image. | It has no face or facial-zone selection: equal pixels in two locations receive equal processing. It can affect background and clothing. |
| Selected-person `faceBrightness` in [session.mjs](../apps/web/src/session.mjs), [faces.mjs](../apps/web/src/processing/faces.mjs) and [editor-ui.mjs](../apps/web/src/editor-ui.mjs) | Typed `face_brightness` adjustment and actual face-oval pixel change. | Its mask is explicitly a face-oval polygon, not a key facial makeup-highlight zone map. The typed portrait contract has no `makeup_highlight` target. |
| Owner-painted [Local Levels](../apps/web/src/processing/local-levels.mjs) | Can brighten only an explicitly supplied coverage mask. | The caller paints/chooses the area; there is no automatic selection of makeup-highlight regions or dedicated cosmetic intensity semantics. |
| Global Glow/Halation and white-highlight effects | Can make bright parts look luminous. | They are not a bounded, face-aware makeup operation. |

At the original audit, the generic Recipe validator could structurally retain an invented `extendedParameters.makeupHighlight` object while the [Web renderer](../apps/web/src/processing/pure.mjs) rejected it. The subsequent [typed Recipe change](../apps/backend/src/photo-policy.ts) now rejects that invented alias with `INVALID_MAKEUP_HIGHLIGHT_MANUAL_ALIAS` and accepts only a bounded optional `makeupHighlightManual` document containing Asset UUID, Original SHA, person UUID, full dimensions, normalized ADD/ERASE strokes and Intensity. It stores no bitmap, saved revision or caller-authored permission. The separate [manual pixel component](../apps/web/src/processing/manual-makeup-highlight.mjs) reuses Local Levels only inside an explicitly supplied, photo/person-bound mask. Its `ownerConfirmed` and provenance strings are caller assertions, **not** authentication or proof that the mask covers a real facial highlight zone. Even the typed extension is still refused by the current Web renderer with `UNSUPPORTED_WEB_ADJUSTMENT`; there is no product Editor, Session save/reload or Final route for it. A fabricated portrait target remains rejected by the typed portrait validator. The [dedicated audit tests](../apps/web/tests/makeup-highlight-completion-audit.test.mjs) pin these present fail-closed boundaries while retaining the original gap as history. Existing Undo/Redo, save, Preset, Sync and Final plumbing apply to their existing controls only. Face processing must also retain the existing [privacy gate](../apps/web/src/person-privacy.mjs).

## Safe next increment, not product completion

A limited **SUITE manual facial-highlight-area adjustment** now has a pure mask-gated sRGB8 processor and a typed normalized stroke document. The next missing step is a runtime that re-rasterizes authenticated owner strokes independently for Proxy/Final, binds the selected person and saved revision to a fresh Asset/Original/permission decision, and refuses a missing or ambiguous face-region mask. Then connect UI, Undo/Redo, CAS save/reload, Preset eligibility, export and regression tests without changing Original. The stored document intentionally omits saved revision and authority claims; those belong in the runtime/CAS gate. The pure function's mask-role assertion alone is insufficient.

Even if this manual path works, it is **not** the source's automatic facial-zone detection or validated makeup look. Automatic key-area selection would need its own model/provenance, consent/privacy review, multi-person identity binding and representative real-photo/RAW quality evaluation. No synthetic numerical test establishes visual equivalence. Real RAW, device, Cloud, cross-platform behavior and source-product parity remain **NOT_RUN / NOT_PROVEN**. The 44-candidate completion count remains unchanged.
